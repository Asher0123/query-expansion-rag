# Similarity Metric Choice

## Why Cosine Similarity Was Chosen

This project uses **Cosine Similarity** for semantic retrieval.

The embeddings generated by the sentence-transformer model represent semantic meaning in high-dimensional vector space. In semantic search systems, the *direction* of vectors is generally more important than their absolute magnitude.

Cosine similarity measures the angle between vectors and determines how semantically similar two pieces of text are.

The implementation uses:

```python
faiss.normalize_L2(embeddings)
index = faiss.IndexFlatIP(dimension)
```

After L2 normalization, the inner product operation effectively becomes cosine similarity.

---

# Cosine Similarity vs Euclidean Distance

| Metric | Description | Characteristics |
|--------|-------------|-----------------|
| Cosine Similarity | Measures angular similarity between vectors | Focuses on semantic direction rather than magnitude |
| Euclidean Distance | Measures straight-line distance between vectors | Sensitive to vector magnitude and scaling |

---

## Why Cosine Similarity Fits Semantic Search Better

In semantic retrieval systems:
- two semantically similar sentences may have different vector magnitudes
- semantic meaning is better captured through vector orientation
- embeddings from transformer models are commonly optimized for cosine-based comparison

Example:

```text
"What is AWS?"
```

and

```text
"Explain Amazon Web Services"
```

may differ in magnitude but still point in similar semantic directions.

Cosine similarity therefore produces better semantic retrieval performance for natural language queries.

---

## Why Euclidean Distance Was Not Used

Euclidean distance is more suitable when:
- absolute geometric distance matters
- vector magnitude carries important information
- embeddings are not normalized

However, for transformer-based semantic embeddings:
- magnitude is often less meaningful
- Euclidean distance can become unstable in high-dimensional spaces
- cosine similarity generally produces better retrieval relevance

# Production Migration to Vertex AI Vector Search (Matching Engine)

In production, the FAISS-based local vector store can be migrated to Google Cloud Vertex AI Vector Search (Matching Engine).

---

## Proposed Production Architecture

```text
Document Ingestion
        ↓
Chunking Pipeline
        ↓
Embedding Generation
        ↓
Vertex AI Vector Search Index
        ↓
Semantic Retrieval API
        ↓
LLM / RAG Pipeline
```

---

# Migration Steps

## 1. Replace Local FAISS Index

Current local implementation:

```python
faiss.IndexFlatIP()
```

would be replaced with:
- Vertex AI Vector Search Index
- Approximate Nearest Neighbor (ANN) search infrastructure

This enables:
- distributed retrieval
- horizontal scalability
- low-latency semantic search

---

## 2. Store Embeddings in Vertex AI

Generated embeddings would be uploaded to:
- Vertex AI Index
- along with metadata such as:
  - source
  - page number
  - chunk id
  - document type

This supports:
- metadata filtering
- scalable retrieval
- enterprise search workflows

---

## 3. Retrieval via Vertex AI Endpoint

Instead of:

```python
index.search()
```

the system would:
- deploy the index to a Vertex AI Index Endpoint
- query embeddings through Vertex AI APIs
- retrieve nearest semantic neighbors from managed infrastructure

# Summary

Cosine similarity was selected because it is more suitable for semantic retrieval tasks involving transformer-generated embeddings.

The current FAISS implementation provides an efficient local retrieval system for experimentation and benchmarking, while Vertex AI Vector Search would provide scalable, production-grade semantic retrieval infrastructure suitable for enterprise RAG systems.
